# either

**The internet's arena.** Two sides, one clock, stablecoin backing. When the round closes
it settles, and the winning side can turn its backing into a token launch.

The authoritative description of the mechanism is
[web/src/content/docs.md](web/src/content/docs.md), which is also served at `/docs` in the
app. This file describes the code: what is in the tree, how the pieces fit, and how to run
them.

## How money moves in a v1 round

```
user wallet (USDG)
  │  ① the only transaction the user signs:
  │     DepositRouter.deposit(side, amount, launchBps)      — or depositWithPermit(…)
  │     moves USDG and records the backing atomically
  ▼
per-user custodial EOA                 generated by the platform, private key sealed in the database
  │  ② DepositIndexer sees the `Backed` event, waits CONFIRMATIONS blocks
  │     VaultDepositExecutor runs approve + ERC4626.deposit from that account
  ▼
ERC-4626 vault
  │  ③ yield accrues against the account's shares
  ▼
withdrawal: the user signs a message, never a transaction
     WithdrawalService: vault.redeem → 10% of positive yield to the fee recipient
                      → USDG back to the user's wallet → record on the ledger
```

Settlement happens at `endTime`: the side with more valid backing principal wins and the
figures freeze. Losers redeem everything. Winners redeem everything except the
`launchBps` share of principal they locked on their first deposit, which stays committed
until the launch window closes and `finalizeLaunch()` decides whether the launch proceeded.
A failed or ineligible launch releases those commitments back to redeemable.

Yield never enters a launch, and the losing side's capital never enters the winner's launch.

### Yield display

Figures shown by either are **net** — the vault's actual performance minus the 10% protocol
fee, computed per user by [`splitYield`](server/src/yield/math.ts). Funds pass through
custodial accounts, so numbers on any third-party vault interface are gross and cannot be
matched to an individual user. Do not point users at one.

## Contracts

### `EitherRoundV2`

A ledger, not a vault. It records who backed which side, decides the winner, and tracks
launch commitments. Three writers:

- **router** — the sole caller of `recordBack`, so the ledger cannot miss a deposit;
- **recorder** — the backend hot key: `registerAccount`, `recordWithdraw`, `recordRedeem`,
  `releaseLaunch`, `recordLaunchSpent`;
- **owner** — rotates the recorder and router, pauses deposits.

`settle()` and `finalizeLaunch()` are permissionless and idempotent; the backend calls them
on a timer, but anyone may.

Round parameters are immutable at construction. The deploy script's defaults:

| Parameter | Default |
|---|---|
| Sides | `arc` vs `robinhood` |
| `endTime` | `1790380800` — 2026-09-26 00:00:00 UTC |
| Launch window | 7 days after settlement |
| Backing threshold `H_B` | 1 USDG |
| Launch threshold `H_L` | 1 USDG |
| Per-account cap | 100 USDG |
| Round cap | 2,000 USDG |

The two caps are contract-enforced, not UI-enforced. `launchBps` is locked on a user's
first deposit; a later deposit with a different value reverts with `LaunchBpsLocked`
rather than silently keeping the old one.

### `DepositRouter`

Holds nothing. `deposit` needs a prior `approve`; `depositWithPermit` takes the allowance
from an EIP-2612 signature, so the user sees one prompt instead of two. If the permit has
already been spent by a front-runner but the allowance is sufficient, the permit is skipped
rather than reverted.

## Backend

One process ([server/src/index.ts](server/src/index.ts)) runs the API and five serial
loops, so the recorder's nonce only ever advances from one place:

| Loop | Interval | What it does |
|---|---|---|
| `indexer` | 30s | follows `Backed` events, queues a vault deposit per event |
| `vault-deposit` | 30s | approve + `ERC4626.deposit` from the custodial account |
| `withdrawals` | 30s | walks each open withdrawal through its state machine |
| `settle` | 20m | `settle()` at the cutoff, `finalizeLaunch()` when the window closes |
| `snapshots` | 10m | records `totalAssets` / `totalSupply` for apy and reconciliation |

Startup refuses to run if the vault's `asset()` is not the configured USDG, or if the RPC
reports a different chain id than `RH_CHAIN_ID`.

Withdrawals are whole-position and resumable:
`pending → (release) → redeeming → redeemed → paying → paid → recording → done`, with every
transaction hash persisted, so a crash resumes at the last completed step instead of paying
twice.

### API

Reads are open — everything in them is onchain or derived from it. Writes carry a fresh
wallet signature over a single-use nonce bound to the domain and the action; there are no
sessions.

```
GET  /api/health
GET  /api/round                    round state + vault info + fee recipient
GET  /api/nonce                    single-use nonce, 10 minute ttl
GET  /api/position/:address        principal, shares, net yield, launch commitment
GET  /api/withdrawals/:address
POST /api/account                  create/return the custodial account, bind it onchain
POST /api/withdraw                 { side, kind: pre_settlement | redemption | launch_release }
```

### Custodial keys

One EOA per user per round. The private key is sealed with envelope encryption
([keys/envelope.ts](server/src/keys/envelope.ts)): a per-secret AES-256-GCM data key wrapped
by a KEK that lives outside the database, with the account's identity as additional
authenticated data — so a ciphertext row moved between accounts fails authentication instead
of decrypting to the wrong key. The database stores only ciphertext. Keys are unsealed only
inside `withSigner`, and the API type for an account has no field a private key could travel
in.

`KEY_PROVIDER=local` wraps data keys with `KEK_HEX` from the process environment. That is
the current deployment choice for the demo: the KEK is in the server env (`chmod 600`, with
one offline backup), never in the database or this repository. Swapping in a KMS or Vault
provider means implementing `KeyProvider`; the envelope format does not change.

### Reconciliation

`npm run reconcile` recomputes what every custodial account should hold and compares it with
the chain — shares against `vault.balanceOf`, principal against the ledger, and loose USDG
against zero. It prints every difference and exits non-zero, so it can gate a deploy or run
from cron.

## Running it locally

Prerequisites: node 20+, [foundry](https://book.getfoundry.sh/), postgres 14+.

### Contracts

```sh
cd contracts
forge install foundry-rs/forge-std      # lib/ is gitignored; needed once
forge fmt && forge test -vv && forge coverage
```

To exercise the deploy path without spending anything, fork mainnet:

```sh
anvil --fork-url https://rpc.mainnet.chain.robinhood.com/
RECORDER_ADDRESS=0x70997970C51812dc3A010C7d01b50e0d17dc79C8 \
  forge script script/DeployV1.s.sol --rpc-url http://127.0.0.1:8545 --broadcast \
  --private-key 0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80
```

The script prints the three `NEXT_PUBLIC_*` values the web app needs.

### Server

```sh
docker run -d --name either-pg -p 5433:5432 \
  -e POSTGRES_USER=either -e POSTGRES_PASSWORD=either -e POSTGRES_DB=either postgres:16

cd server
cp .env.example .env            # fill in the blanks — see below
npm install
npm run migrate                 # applies src/db/schema.sql
npm run dev                     # :8787
npm run typecheck && npm test
```

`.env` must be filled before the process will start — configuration is parsed once with zod
and a missing value fails loudly at startup rather than as an `undefined` inside the
executor. The blanks in `.env.example` are:

| Variable | What it is |
|---|---|
| `ROUND_V2_ADDRESS`, `DEPOSIT_ROUTER_ADDRESS`, `V1_DEPLOY_BLOCK` | printed by `DeployV1.s.sol` |
| `RECORDER_PRIVATE_KEY` | hot key that writes to the ledger |
| `GAS_FUNDER_PRIVATE_KEY` | hot key that tops custodial accounts up with ETH |
| `KEK_HEX` | 32 bytes of hex; `openssl rand -hex 32` |
| `DATABASE_URL` | postgres connection string |

Gas is ETH on Robinhood Chain, not USDG, so the funder account needs an ETH balance;
`CUSTODIAL_GAS_TARGET_WEI` is the level each custodial account is kept at, topped up when it
falls below half.

### Web

```sh
cd web
cp .env.example .env            # arc/v0 variables
npm install
npm run dev                     # :3000
npm run typecheck && npm run build
```

Environment names keep the `NEXT_PUBLIC_` prefix from the app's Next.js origins — honoured
through `envPrefix` in [vite.config.ts](web/vite.config.ts) and read via `import.meta.env`.
They are baked in at build time, so changing `.env` needs a rebuild, not a restart.

`.env.example` covers the v0 arc variables. The v1 page additionally needs:

```
NEXT_PUBLIC_ROUND_V2_ADDRESS=
NEXT_PUBLIC_DEPOSIT_ROUTER_ADDRESS=
NEXT_PUBLIC_V1_DEPLOY_BLOCK=
NEXT_PUBLIC_API_URL=http://localhost:8787
```

USDG, the vault address and the Robinhood Chain parameters default to their mainnet values
and only need overriding to point a build at a fork. Deployment notes for the static build —
including the nginx SPA fallback — are in [web/README.md](web/README.md).

## Conventions

- Amounts are `bigint` base units everywhere, converted to strings only at the rendering
  boundary ([web/src/lib/format.ts](web/src/lib/format.ts)). Nothing numeric rides through
  `number`; the API's wire format for a `bigint` is a decimal string, and postgres columns are
  `numeric(78,0)`.
- ABIs are hand-written in [contracts.ts](web/src/lib/contracts.ts) /
  [contractsV1.ts](web/src/lib/contractsV1.ts) and [abis.ts](server/src/chain/abis.ts) —
  no artifact JSON is imported.
- Contracts use custom errors rather than `require` strings, CEI ordering with a reentrancy
  guard, and one aggregate `getXxx()` view per screen so the frontend reads state in a single
  call.
- Interface copy is lower case, written lower case in the source — not flattened by a global
  `text-transform`, which would also flatten addresses and env names.
- Comments explain why, not what.

## Custody and security

**This is a custodial design.** After a deposit, USDG sits in an address whose private key
the platform generated and holds. The platform moves funds into the vault and executes every
withdrawal. Key compromise, operational failure or insider misuse means total loss of the
funds in a custodial address. Encryption at rest and scoped hot keys reduce that risk; they
do not remove the custody relationship.

Standing rules for anyone working in this tree:

- Private keys, mnemonics, KEKs and `.env` files never enter the repository or the logs.
  `server/.env*` is gitignored; keep it that way.
- Custodial keys are decrypted in memory only, zeroed immediately after use, and never
  logged, persisted, returned by the API, or included in an exception.
- The recorder and gas funder are hot keys with recording and execution rights only. The fee
  recipient is a separate address.
- The contract caps (100 USDG per account, 2,000 USDG per round) are the blast radius. They
  belong in the contract, where they are now — not in the UI.
- The UI must state plainly that this is a demo deployment, that funds are custodial, and
  that there is no insurance or guarantee of any kind.

### Invariants

These are what the tests are written against, and what `reconcile` checks:

1. A user's withdrawable amount never exceeds what their custodial account can redeem from
   the vault.
2. `protocol fee + user net yield = gross yield`, and the fee is zero whenever gross yield
   is not positive. Principal is never charged; a loss is never topped up.
3. The same principal is never simultaneously redeemed and committed to a launch.
4. Losing-side capital never enters a launch.
5. Winning-side capital that was not explicitly committed never enters a launch.
6. Settlement, launch success and launch failure each finalize exactly once.
7. Post-settlement withdrawals do not change the winner.
8. `launchBps` is written once per user per round.

## Status

The v1 contracts, backend and page are implemented and covered by tests
(`forge test`, `npm test` in `server/`). What that does not include: an independent security
review, a production legal and compliance position for holding user funds, or any guarantee
about the underlying vault. The round is a demo deployment on mainnet with real funds and
contract-enforced caps sized accordingly.

Production parameters that remain open are listed at the end of
[docs.md](web/src/content/docs.md). Change the mechanism there first — it is the reference
the contracts and the UI are written against.
